4. SOFTWARE DESCRIPTION

4.1 CyberRMF Integrate provides the following core capabilities:
(a) Artifact management — interactive Security Control Traceability Matrix (SCTM), Plan of Action and Milestones (POA&M), Continuous Monitoring (CONMON), policy and procedure documents, and related compliance artifacts.
(b) Inventory tracking — asset inventory with NIST SP 800-53 control requirement mapping, native drag-and-drop floorplan layouts, and end-of-life tracking.
(c) Third-party integration — optional outbound connections to SIEM, antivirus / endpoint detection and response (EDR), and vulnerability management platforms configured by the Licensee.
(d) STIG validation — import and parsing of XCCDF benchmark files for Security Technical Implementation Guide compliance checks.
(e) Auditing — network diagnostics (ping, traceroute, DNS lookup) and cyber hygiene health dashboards.
(f) Workspace export and import — full workspace packaging as ZIP archives for transfer between users, organizations, or Security Control Assessors (SCAs).

4.2 CyberRMF Admin Tools provides the following capabilities:
(a) Ports, Protocols, and Services (PPS) generation — enumerates running processes and active network connections on target hosts.
(b) Installed software inventory — collects software lists from Windows (WMI/CIM) and Linux (package manager queries) systems.
(c) Encryption verification — checks BitLocker status (Windows) and block device encryption (Linux) on target hosts.
(d) Log collection — enumerates and exports Windows event logs and Linux system logs from remote systems.
(e) Active Directory user enumeration — queries AD for user accounts using PowerShell or LDAP.
(f) DNS spot check — performs local nslookup operations to verify hostname and IP consistency against inventory records.
(g) Domain join verification — queries Active Directory for domain-joined computer objects.

4.3 Shared Workspace. Admin Tools writes scan results to the shared Workspace directory. Integrate reads these results to populate dashboards, reports, and artifact views. The two applications communicate exclusively through the shared file system and do not use inter-process communication, network sockets, or any external relay.

6. THIRD-PARTY INTEGRATIONS

6.1 Outbound Connections Only. Integrate can establish outbound network connections to Third-Party Services configured by the Licensee. These connections are initiated solely at the Licensee's direction using URLs and credentials provided by the Licensee. The Software does not expose an API, does not accept inbound connections, and does not function as a network service.

6.2 Supported Integrations. As of this version, Integrate supports connections to Splunk, ELK/OpenSearch, Trellix ePO, CrowdStrike Falcon, Microsoft Defender for Endpoint, Tenable.sc, Nessus, and generic REST API endpoints for SIEM, antivirus, and vulnerability management platforms.

6.3 TLS Certificate Verification. Integrate verifies the TLS certificate of every Third-Party Service it connects to over HTTPS before it sends any data or credentials. A certificate that passes standard verification is accepted. If a certificate cannot be verified (for example, because it is self-signed, was issued by a certificate authority that the Software does not recognize, was issued for a different server name, or has expired), Integrate closes the connection without sending anything and shows the certificate's details, including its SHA-256 fingerprint. The Licensee may then choose to trust that exact certificate for that server. After that, Integrate accepts the trusted certificate for that server, and if the server presents a different certificate that cannot be verified, Integrate refuses the connection until the Licensee reviews and trusts it. Trusted certificates are stored for each user on each device. The Licensee is responsible for confirming that a certificate belongs to the intended server before trusting it. Connections to a Third-Party Service configured with an http:// address are not encrypted.

6.4 SSH Host Key Verification. Admin Tools verifies the host key of every remote system it connects to over SSH, in the manner of OpenSSH's known-hosts file. Before a scan, Admin Tools reads the host key of each target that has no approved key on the device, without attempting to log in, and asks the person running the scan to approve the new hosts and their key fingerprints. Connections that send credentials accept only the approved key: a host that has not been approved, or whose key has changed, is refused before any credentials are sent. Approved host keys are stored for each user on each device and can be reviewed and removed in Admin Tools. The Licensee is responsible for confirming that a host key belongs to the intended system before approving it.

7.5 Workspace Locking. The Software uses cooperative file-based locking to prevent concurrent conflicting edits to the same Workspace. Lock files are stored in the Workspace's .cyberrmf directory and identify the active user by operating system username and hostname.

7.6 Activity Log. Each application keeps an Activity Log of actions taken in a Workspace, such as data saved or deleted, files added or removed, scans run, integrations used, and errors. Each entry records the time, the application and its version, and the operating system user name, domain, and computer name of the person who took the action. Entries are written to the Workspace's .cyberrmf directory, where other users of the Workspace can view them, and are chained so that later edits can be detected. Technical details of errors, such as stack traces, are kept only on the device where they occurred. Each application also records, once per launch, basic system details (the Windows version, application and runtime versions, memory and free disk space) and, if an application or one of its processes crashes, a crash dump file, which can contain memory contents from the time of the crash. These are also kept only on the device; technical details of errors and crash dumps are deleted once they are fourteen (14) days old, the next time the application runs. The Activity Log is not transmitted to CyberRMF LLC.

7.7 Support Bundles. A user may choose to create a support bundle: a ZIP file, saved where the user chooses, containing the device's recent Activity Log entries, error details, system details, license status and, only if the user selects it, crash dumps. Support bundles never contain Workspace file contents, saved credentials or the license key. The Software does not send support bundles anywhere; the user decides whether and how to share one. If a user sends a support bundle to CyberRMF LLC, CyberRMF LLC uses it only to investigate the reported problem.


8. NETWORK OPERATIONS

8.1 Integrate Network Activity. Integrate performs local network diagnostic operations, including ICMP ping, traceroute, and DNS lookups (nslookup), for auditing and cyber hygiene assessment purposes.

8.2 Admin Tools Network Activity. Admin Tools performs targeted remote operations against hosts listed in the Licensee's inventory. These operations include WMI queries (TCP port 135 and dynamic RPC ports), WinRM sessions (TCP ports 5985/5986), and SSH connections (TCP port 22). Admin Tools does not perform subnet sweeps, port scanning of arbitrary hosts, or network discovery beyond the hosts explicitly listed in the inventory.

8.3 Log Collection. Admin Tools can copy Windows event log files (.evtx) and Linux system logs from remote hosts to a local directory selected by the Licensee. To collect Windows event logs, Admin Tools exports them on the remote host into a temporary folder it creates under that host's Windows Temp folder, copies them from there, and then deletes that folder; over WMI it starts the Windows event log utility (wevtutil.exe) on the remote host to do so. The Licensee is responsible for securing collected log data in accordance with organizational policies.

8.4 Licensing Traffic. The only connections the Software makes to CyberRMF LLC or its service providers are the license activation, re-validation, and deactivation requests described in Section 3.
